# Internal agent tasks

`/tasks` is a calendar of internal Samwise work and dated Todoist tasks, including human actions. Creating an internal task requires a title and a future date/time; instructions and a checklist can be added. Without a custom checklist, the title becomes its single outcome. There is no undated backlog. Todoist remains the source of truth for imported human work.

An instance owns its instructions, checklist, evidence and next check time. A recurring template owns the recurrence and the instructions/checklist copied to new instances. Calendar entries projected from a recurrence are materialized when opened for editing; the scheduler normally keeps only the nearest future instance. Editing an existing instance never modifies its template. Editing a template affects only instances generated later. Disabling a template stops its instances from starting.

The first/last weekday presets mean Monday–Friday, not public-holiday calendars. Recurrences use five-field Cronos expressions with an explicit time zone; monthly day 31 skips months without that day. The calendar is displayed in Europe/Prague. Each instance retains its original occurrence even if its next check is moved.

Every 30 seconds the scheduler generates the next occurrence and dispatches due tasks. It skips missed repetitions after downtime, retaining the already-materialized due instance and one upcoming instance. Dispatch atomically stores the task's run link, a work item, and a pending input. Existing inbox recovery resumes that input after a crash. Explicit delegated tasks bypass Intake and enter normal Planning. Approval and execution permissions remain unchanged.

The task's next check is cleared while a run is active. The linked work item holds questions, approval, errors and uncertain writes. Another run cannot start until that work item is terminal. Verified effects belong in checklist evidence; an unfinished checklist needs an explicitly scheduled next check. Successful external operations with a missing task continuation are surfaced as NeedsAttention, preserving outputs. No silent retry is created. At startup, before accepting work, the single Samwise web process converts interrupted Executing work and its running execution invocations to OutcomeUnknown. Upstream agents may still be running; the owner must reconcile them and their effects before closing the old work item. Nothing is replayed. Parallel web replicas are outside this deployment model. A new self-check also blocks on its originating intervention until that intervention is terminal. Owner edits withdraw an unexecuted pending work item atomically with the task change; executing or uncertain work must be resolved before owner edits.

## MCP and Gateway

The Samwise MCP server exposes `list_agent_tasks`, `get_agent_task`, `save_agent_task`, `save_agent_task_progress`, `list_agent_routines`, and `save_agent_routine`. Updates require the current stored version. During approved Execution, use only `save_agent_task_progress`, which requires the current `executingWorkItemId`; an unrelated run cannot alter another pending run. New self-checks always inherit that executing origin. `save_agent_task` is the separate owner editor and withdraws any unexecuted pending plan. A completed checklist item requires evidence. Routine creation requires owner delegation; it grants no additional execution authority.

After deployment, grant task read tools to the Planning profile and task reads and only `save_agent_task_progress` to the appropriate Execution profiles through the existing Gateway configuration. For automatic self-checks, the selected playbook must authorize the scoped check and its task progress/continuation operation, and the restricted profile must include the necessary tools. Never grant the owner editor `save_agent_task` to an Execution profile. Do not grant routine/configuration mutations just to support one-off self-checks. Missing tools remain a visible capability gap.

## Todoist external source

Todoist configuration lives at `/tasks/sources/todoist` under the task calendar. All dated tasks assigned to the owner or nobody are imported, including older overdue tasks. Tokens and explicit project/label exclusions are retained. Legacy inclusion lists and the old initial overdue-age limit no longer restrict import. Labels and projects are context, not a delegation gate. The old Intake polling route is removed; old pending Todoist inputs are retired without creating work. The source module adopts one existing live work item when importing, preserving its approval/question/evidence; multiple live legacy work items require reconciliation.

Imported entries stay on the source due date in the calendar even after an assessment or when a separate internal check is scheduled. At the due check, Planning assesses what Samwise can usefully do under the most specific playbook. For human work with adequate tracking and no useful operation or justified later check, `no_longer_relevant` ends only the intervention. The active Todoist task and unfinished checklist remain open and visible; unchanged polling does not schedule another intervention. `already_resolved` does not bypass the unfinished-task progress guard. Useful evidence-based later checks use the linked internal task, not a postponed Todoist deadline. Completion in Todoist requires current evidence for the exact outcome and recurring occurrence plus normal approved execution. Being personal, physical, overdue, or unsuitable for automation is never completion evidence.

Todoist owns title, instructions and its due date. Samwise owns the checklist and next check; repeated unchanged syncs never overwrite either or invalidate an approval. Custom checks survive source edits; a postponed source date moves only an untouched initial due check. The full source is fingerprinted separately from prompt excerpts. A changed instruction on a completed task adds a review step, retaining verified effects; a date-only postponement does not reopen them. Postponing and restoration of the same occurrence retain its checklist. A monotonic known completion counter (or an observed completion followed by a later recurring due date) distinguishes a new occurrence, whose checklist starts clean. Missing or regressed counters never reset the baseline. New external generations inherit unresolved execution origins; restoring access never resolves a pending failure. Source completion/deletion/out-of-scope/undated status stops further checks.

An imported Todoist task can be removed from Samwise with **Remove from Samwise** in its task dialog (or the owner MCP tool `dismiss_todoist_task`). The removal is a soft delete of that Todoist task ID, covering every future occurrence and generation: its latest Samwise task is retired with the `dismissed` state, which synchronization never imports past; unexecuted work is discarded, while an executing or uncertain run is never interrupted. Nothing is written to Todoist. The task leaves the calendar, and its document and work items remain readable. **Removed tasks** at `/tasks/sources/todoist` (or `restore_todoist_task`) restore it; the next sync then imports it in the normal way. Missing access is shown as unavailable, never as completion. Exact source refresh runs before dispatch and execution; errors block the operation. Source writes remain normal approved MCP actions.

Deploying this change broadens import beyond previous project/label selections and overdue-age limits; explicit exclusions still apply. Reconcile legacy records and corresponding T3 schedules to avoid duplicate automations. No T3 schedules are changed by synchronization.

## Removed waiting state

New Planning and Execution results cannot return `awaiting_external_event`. Execution success verifies this intervention's approved result; a draft or manual handoff does not assert sending, payment or collection. Future work is represented by a dated internal task.

The startup migration converts legacy waiting work items to NeedsAttention, removes their current plan reference and pending question, advances the revision, and preserves the waiting reason and previous planning feedback. Existing comments, plans, successful effects and invocation history remain intact. Migration does not execute or replan anything.
