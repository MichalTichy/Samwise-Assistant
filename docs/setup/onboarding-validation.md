# Goal-first onboarding conversation validation

Validated on 2026-11-15 against the local setup guide and skill. This is conversational forward-testing of the assistant's decisions and explanations. Deployment, account authorization, catalog, model and provider outcomes were supplied by an explicitly simulated harness. These tests do not establish live provider connectivity, product inference, ingestion, or execution. The earlier live local-demo checks are recorded separately in [validation.md](validation.md).

## Test method

Fresh assistant agents read the guide and setup skill without previous conversation history, earlier rehearsals, intended replies, or review findings. Their first user message was the short prompt printed in the README. Independent user agents knew ordinary work needs and preferences, but did not read the guide, scoring criteria, or technical setup instructions. They disclosed information in response to the conversation, rather than supplying a deployment recipe or a finished test case.

The parent relayed the conversations and supplied labelled environmental outcomes only after the assistant requested them. No connected production service was called. Exact messages, requests, results and guide revisions were retained in the ignored `.data/setup-ux-20261115/` directory. Review copies remove internal harness blocks and decode JSON; they do not rewrite the messages. The parent reviewed the complete user-facing conversations and the operational requests.

## Cases exercised

- **New nontechnical owner:** work arrives in Teams and Microsoft 365; the owner forgets promises and already uses Todoist. The assistant proposed the whole promise → reviewed task → matching sent-email evidence → reviewed completion scenario before deployment questions. It explained each separate sign-in, generated internal configuration through the harness, excluded personal sources, and retained the chosen review policy. After the first result, the owner requested reply drafts; the assistant reused existing connections and proposed only the additional draft scope, without repeating unrelated logins or enabling sending.
- **Existing installation:** a coordinator wanted reviewed client replies and meeting-time proposals using work Outlook. The assistant reused the existing installation, keys, models and unrelated rule; it did not add Teams or a task manager. The fixture withheld organization consent. The assistant preserved pending state, explained the administrator dependency, continued independent preparation and resumed after consent. At handover the owner asked only what one Teams chat would require; the assistant explained the additional scenario and made no connection or configuration request.
- **Fresh handover regression after corrections:** the assistant summarized the first result, linked the actual local tune-up skill, explained occasional tuning and invited more scenarios while setup remained active. When the owner said they were done, it requested closure, waited for the observed fixture result, and then ended without another questionnaire.

## Corrections made during review

The guide now asks about sources of work and initial needs before infrastructure, recommends only relevant incoming sources and action/context tools, gives a complete relatable situation and confirms that direction once. Owner sign-ins and manual actions get a reason and a concrete next step; internal API keys are the assistant's configuration work. Examples and tests are proposed by the assistant rather than assigned to the owner as technical homework.

Two handover defects were demonstrated and corrected: an unverified public link was used for an unpublished local tune-up skill, and temporary setup access was closed before asking about additions. The final instructions use an accessible local/installed skill link and invite additions before final closure. Closure still occurs when the owner is finished or the session must pause; it must not remain open indefinitely. The fresh handover regression exercised these corrections.

The owner's later steering is reflected in the final guide: ordinary app/calendar/environment defaults are used without making timezone an onboarding topic; only a concrete conflicting fact affecting the result justifies clarification. The standalone timezone experiment was discontinued and is not counted as an acceptance case.

Subsequent owner review identified two more issues in the new-installation dialogue: deployment choice was reduced to an always-on host question without first inspecting Docker, and the owner-account email question unnecessarily required a Microsoft 365 work address. The guide and setup skill now call for Docker discovery and help choosing local execution or a Compose deployment on another host, explaining that Compose also works locally. Owner identity is explained separately from mailbox authorization. Inspection of `OwnerIdentityInitializer` and the login page confirmed that the email identifies the single owner and is displayed at sign-in, which uses a separate Samwise password. These are targeted instruction corrections checked by source review and skill validation; the earlier preserved conversations have not been rewritten or rerun for these changes.

## Owner-created account follow-up

The owner subsequently chose a simpler flow: after deploying Samwise, open a private installation link and let them enter their email and password directly in the web UI. The guide, installed setup skill and helper now use that flow instead of asking for an owner address or generating a user password. Existing installations retain sign-in. The helper's explicit `--owner` option remains available for legacy unattended provisioning.

Registration was verified against real disposable PostgreSQL and the production-derived application image, without connecting real provider accounts. The working checkout passed 270 .NET tests; the production-derived source passed 266, both including seven registration integration tests and five token cases. All 13 helper tests passed. Integration checks covered concurrent creation, consumed/invalid links, restart persistence, legacy-owner/password preservation and input validation. HTTP form checks covered missing/invalid tokens, required antiforgery, password confirmation, no password echo on validation errors, automatic sign-in, private response headers, registration closure, and sign-in with the same owner/password after restart. These are actual application/database checks, not the earlier simulated dialogue fixtures.

The original conversations remain unchanged and still show the older account-creation interaction. No new independent-agent conversation rehearsal was run for this focused follow-up. Deployment uses the recorded production source plus the registration patch, preserving newer production behavior rather than replacing it with the older working checkout. Private image, source hashes, test logs and rollout evidence are recorded under ignored `.data/owner-registration-20261115/`.

## Full conversation after web-registration deployment

A fresh assistant read the current guide and skill, and a separate nontechnical Czech user agent supplied their own replies without reading the guide or review criteria. The complete conversation reached trial approval, cleanup, the invitation for other scenarios and final closure. All deployment, registration, authorization, provider and inference results in this run were explicit fixtures; this is conversation evidence, not another live installation test. The earlier real registration HTTP checks remain separate.

The retained review copy contains 40 unchanged user-facing messages (17 user, 23 assistant). Raw operations/fixture evidence, the review transcript and the user agent's separate debrief are stored under ignored `.data/setup-ux-registration-20261115/`. A duplicate opening caused by the parent relay was never delivered to the user and is explicitly documented in that directory.

The process was understandable but still too demanding for a first setup. Creating an owner through the web required no chat disclosure of email/password and prompted no confusion. Concrete proposal review and the distinction between draft saving and sending worked. The user questioned Docker, was surprised by Codex sign-in while expecting Microsoft, and delegated the unnecessary model-choice question back to the assistant. The final message also needed a concrete next action rather than a general remaining-phases list. Cleanup, result summary, tuning explanation and the next-scenario invitation were crowded into one response.

The same run exposed a capability limit rather than a wording problem: current Teams input exclusion lists do not guarantee that only selected chats are ever read, including newly created chats. The assistant retained this restriction and the user accepted email/Todoist while Teams remained off. No allowlist feature was implemented or claimed by this test.

Corrections in the guide and installed skill explain the AI-account dependency before deployment, introduce Docker in ordinary language, use supported routine model/effort defaults without asking an unfamiliar owner to choose, check the known Teams constraint early, propose the bounded test and cleanup together, separate immediate cleanup from handover and request one actionable next step for any unfinished setup. The original transcript is preserved rather than edited to show these corrections. Focused fresh-agent checkpoints are recorded separately; they are not a second complete conversation.

The exchange is retained unchanged under ignored `.data/setup-ux-refined-20261115/`, with separate requested-operation/fixture evidence and post-conversation debrief. ### Debrief correction: reminders need an attention path

The independent user's post-closure debrief found a material outcome gap: the initial request concerned reminders, but the task trial had only a deadline and the owner did not know how new proposals would reach them without checking the dashboard. The full run therefore is not a complete pass for the original reminder goal. The user also found the confirmations numerous and the separate Outlook consents surprising, while exact-result review and one-action sign-in messages were clear.

After preserving that run, the guide and installed skill were updated to distinguish review notifications, task deadlines and timed reminders; discover actual support and verify owner-observed delivery or name the pending step. The guide now previews required account connections before the first sign-in. These final corrections were not exercised in the full conversation. A fresh focused checkpoint read the final guide against a due-date-only task tool and unapproved browser push. It explicitly said the reminder goal was unmet, distinguished proposal push from deadline reminders, requested browser consent as the one next action, and required owner-observed delivery afterward. It did not invent a reminder argument, ask for an irrelevant hour or claim a delivered notification. The retained reply and private pass criteria are in `reminder-checkpoint.txt`. This is one decision checkpoint, not a second complete conversation or a live delivery test. No timed-reminder or notification feature was implemented by this documentation change.

## Acceptance and limits

Both main conversations showed the requested opening, work-source discovery, concrete proposed scenario, confirmation before configuration, purpose-led access steps, exact-result review, invitation to other scenarios and practical tune-up explanation. The existing-installation case also showed an honest blocked/resumed state. The new-installation case exercised an accepted addition; the existing-installation case respected an information-only addition. The corrected handover was independently re-tested rather than silently editing old dialogue.

The complete flow includes simulated credentials and permission prompts, so those operational steps require separate verification against a real owner's selected accounts. No real completion guarantee follows from supplied fixture outcomes. The guide and skills passed metadata validation; all 11 existing setup-helper tests passed, and `git diff --check` passed. No wording-matching tests are used as evidence of conversation quality.

These rehearsals used local revisions before publication. Until both setup APIs reach their default branches, use the companion branches listed in the root README. The preserved conversations describe the revisions actually tested.
